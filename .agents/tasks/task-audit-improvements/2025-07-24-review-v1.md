# Security hardening and frontend resilience fixes

This change addresses six security and robustness issues across `server.js` and `public/app.js`: path traversal in conversation GET, SSRF via redirect following, missing Secure cookie flag, overly restrictive microphone permission, session token non-revocability on logout, and several frontend reliability gaps (streaming timer leak, LCS diff performance, search debounce, init crash recovery). The approach is conservative — each fix is minimal and local, avoiding structural refactors.

**Watch for:** The SSRF redirect validator checks hostnames but does not resolve DNS, leaving a DNS rebinding window (likely). The `clearSessionCookie` function does not include the `Secure` flag when `TRUST_PROXY` is set, creating a potential cookie mismatch that could prevent logout from clearing the cookie in strict browsers (confirmed). CSRF protection and the file-based user store race condition were identified in the feature spec but not implemented (confirmed, deliberately deferred per findings notes).

## High-level view

The SSRF fix replaces `redirect: "follow"` with a manual redirect loop that validates each hop's hostname against `isBlockedHost`. This closes the original bypass but introduces a new concern: validation happens at the hostname level, not at the resolved IP level, so an attacker-controlled DNS record that resolves differently between the check and the connection remains a theoretical vector.

Session tokens are now revocable via an in-memory deny list checked on every `verifySessionToken` call. The revocation set is periodically pruned, but revoked tokens are forgotten on restart and the lookup is O(n) over the set rather than O(1) via a Map.

The frontend fixes add a guard before `setInterval` to prevent orphan timers, a 2000-line threshold that skips the O(n·m) LCS algorithm, debouncing on the search input, and a try/catch around init rendering that resets corrupted local storage. The init recovery path destroys all conversation data rather than isolating the corrupted entry.

The `clearSessionCookie` function was not updated to include `; Secure` when `TRUST_PROXY` is enabled, which means browsers that received the cookie with the Secure attribute may not clear it properly on logout.

## SSRF redirect validation and DNS rebinding

`isBlockedHost` inspects the hostname string (checking for `localhost`, private IP ranges, link-local addresses, cloud metadata IPs). If an attacker registers a public domain whose DNS record points to `127.0.0.1` or `169.254.169.254`, the hostname check passes but the actual TCP connection targets the internal host. This is a well-known SSRF vector (DNS rebinding / TOCTOU between check and connect).

Mitigation options: use Node's `dns.lookup` to pre-resolve before calling `fetch`, then validate the IP; or use the `lookup` option on the underlying HTTP agent to intercept resolution. Neither is trivial with the global `fetch` API, which is why this is "likely" rather than "confirmed exploitable in this codebase."

## Token revocation scaling

`_isTokenRevoked` iterates the entire Set for each `verifySessionToken` call. If token TTLs are long and logout events accumulate, the linear scan on every authenticated request becomes a concern. A `Map` keyed by `payloadHash` would give O(1) lookup:

```javascript
// Current: O(n) scan
function _isTokenRevoked(payload) {
  const payloadHash = crypto.createHash("sha256").update(payload).digest("hex");
  for (const entry of _revokedTokens) {
    if (entry.payloadHash === payloadHash) return true;
  }
  return false;
}
```

Switching to `Map<payloadHash, exp>` is a one-line structural change with better scaling characteristics.

## clearSessionCookie missing Secure flag

`setSessionCookie` conditionally appends `; Secure` when `CONFIG.trustProxy` is true:

```javascript
const secure = CONFIG.trustProxy ? "; Secure" : "";
res.setHeader("Set-Cookie", `...${secure}`);
```

But `clearSessionCookie` unconditionally omits it:

```javascript
function clearSessionCookie(res) {
  res.setHeader("Set-Cookie", `${CONFIG.auth.cookieName}=; HttpOnly; SameSite=Lax; Path=/; Max-Age=0`);
}
```

Per RFC 6265, to delete a cookie the Set-Cookie header must match the cookie's attributes. When `TRUST_PROXY=true`, the session cookie is set with `Secure`, but the clear attempt does not include it. This could cause logout failures in strict environments.

## Frontend init recovery destroys all data

The catch block wipes `state.conversations` entirely and resets localStorage:

```javascript
} catch (e) {
  state.conversations = [];
  state.activeId = null;
  safeStorageSet(localStorage, LS.convos, "[]");
  renderConversations();
  renderMessages();
  toast("Chat history was corrupted and has been reset.", "error");
}
```

If the corruption is in a single conversation object (e.g., a malformed `messages` array on one item), the entire history is destroyed. A more surgical approach would filter out the corrupted entry and preserve the rest — significant for user trust in a "premium" chat application.

## Diff fallback provides no useful information

When files exceed 2000 lines, the fallback shows all old lines as deletions followed by all new lines as additions. This is functionally a "no diff" — it doesn't help the user understand what changed, just confirms the files differ. For files between 500 and 2000 lines, the O(n·m) table still allocates up to 4 million Int32 entries (~16 MB), which may cause jank on low-memory devices. A middle ground (Myers diff with linear space, or patience diff) would serve better long-term.
